## Abstract

The Hat Standard (Version T) defines a uniform data structure for representing
cosmetic and weapon properties derived from Team Fortress 2 inventory responses.
This specification dictates the abstract properties of a "Hat", the logic for
deriving these properties from standard Steam item payloads, and a strict,
bidirectional text serialization format for transport and storage.

## 1. Abstract Data Model

A conformant "Hat" entity represents the following logical properties:

- **`marketHashName`**: The exact market hash identifier of the item.
- **`tradable`**: A boolean state representing whether the item can be traded.
- **`marketable`**: A boolean state representing whether the item can be sold on
  the Steam Community Market.
- **`craftable`**: A boolean state representing whether the item is allowed in
  crafting recipes.
- **`festivized`**: A boolean state representing whether the item has the
  "Festivized" property.
- **`qualities`**: A list of item qualities (e.g., Unique, Strange).
- **`unusualEffects`**: A list of applied Unusual Effect names.
- **`killstreakers`**: A list of Killstreaker effect names.
- **`sheens`**: A list of Killstreak Sheen names.
- **`warPaints`**: A list of applied War Paint names.
- **`paints`**: A list of cosmetic Paint Color names.
- **`spells`**: A list of applied Halloween Spell names.
- **`killstreakParts`**: A list of applied Strange Part names.

## 2. Derivation Rules (Steam Economy Mapping)

To convert an inventory response to the Hat data model, the properties MUST be
mapped according to the following rules. Any lists generated by these rules MUST
be sorted alphabetically. For sorting, use sequences of UTF-16 code unit values.

Note to implementers, the set of valid BCS characters is rather small. Depending
on string normalization, sorting using your native sort function might provably
yield identical results.

### 2.1 Base Flags

- **`tradable`** / **`marketable`**: Inherited directly from the corresponding
  truthy/falsy state on the root item object.
- **`craftable`**: Logically `false` if any of the item's descriptions reads
  exactly `"( Not Usable in Crafting )"`. Otherwise, `true`.
- **`festivized`**: Logically `true` if exactly one of the item's descriptions
  reads exactly `"Festivized"`. Otherwise, `false`.

### 2.2 Reading Properties

This section defines the procedures for transforming raw Steam Economy "Tags"
and "Descriptions" into the Hat Model’s list properties.

#### 2.2.1 Data Filtering & Preparation

Before extraction, the source data must be filtered according to these rules:

1. **User Applied Descriptions**: When evaluating "Descriptions," implementers
   MUST exclude any entries with a `type` property with the value `"usertext"`.
2. **Property Normalization**: After extraction and before serialization, every
   list MUST be sorted alphabetically based on the resulting string values.

#### 2.2.2 Property Extraction Rules

When matching prefixes, the prefix MUST be the start of the description. When
matching suffixes, the suffix MUST be the end of the description.

For every property, the value is derived from the "System Descriptions" or
"Tags" based on the following logic:

| Property              | Source       | Extraction Rule                                                                                                                 |
| :-------------------- | :----------- | :------------------------------------------------------------------------------------------------------------------------------ |
| **`qualities`**       | Tags         | Select the `localized_tag_name` for every tag where the `category` is exactly `"Quality"`.                                      |
| **`unusualEffects`**  | Descriptions | The substring following the prefix `"★ Unusual Effect: "`                                                                       |
| **`killstreakers`**   | Descriptions | The substring following the prefix `"Killstreaker: "`.                                                                          |
| **`sheens`**          | Descriptions | The substring following the prefix `"Sheen: "`.                                                                                 |
| **`warPaints`**       | Descriptions | The substring following the prefix `"✔ "`.                                                                                      |
| **`paints`**          | Descriptions | The substring following the prefix `"Paint Color: "`.                                                                           |
| **`spells`**          | Descriptions | The substring found between the prefix `"Halloween: "` and the suffix `" (spell only active during event)"`.                    |
| **`killstreakParts`** | Descriptions | The substring found between the leading `(` and the following `:` within lines matching the format `"([Part Name]: [Number])"`. |

#### 2.2.3 Unusual Effects

The **`unusualEffects`** property MUST be set to an empty array if a description
exists that contains the substring `"Case Global Unusual Effect(s)"`.

## 3. The "Basic Character Set" Encoding

To guarantee safe semicolon-delimited transport, all strings must conform to a
standardized escape sequence encoding known as the Basic Character Set.

### 3.1 String Encoding/Decoding

Unencoded input strings containing asterisks (`*`) or carets (`^`) are
considered invalid and MUST be rejected to prevent ambiguous encodings.

An encoded string substitutes specific characters using a strict mapping:

- Spaces are mapped to underscores (`_`)
- Underscores (`_`) are mapped to the sequence `*u`
- Newlines are mapped to the sequence `*n`

A fully encoded string MUST NOT contain any characters outside of the following
allowed set: alphanumeric characters (case-insensitive), accented characters
(`ä`, `é`, `ñ`, `ò`, `ü`), and the specific symbols `_`, `!`, `#`, `%`, `*`,
`'`, `:`, `,`, `.`, `(`, `)`, `-`, and `?`.

### 3.2 List Encoding

When a list of strings is encoded, each individual string is encoded according
to the rules in 3.1. The resulting strings are then joined into a single string
using the delimiter sequence `*c`.

### 3.3 Pseudo-code

To encode a raw string into BCS:

1. Validate that the input contains no `*` or `^` characters.
2. Apply the following transformations in sequence:

```text
FUNCTION encodeString(input):
  IF input contains "*" OR "^": THROW "Ambiguous Encoding Error"
  
  SET result = input
  result = REPLACE_ALL(result, "_",  "*u") // Map existing underscores to *u
  result = REPLACE_ALL(result, "\n", "*n") // Map newlines to *n
  result = REPLACE_ALL(result, " ",  "_")  // Map spaces to underscores
  
  VALIDATE result matches /^[a-z0-9_äéñòü!#%*':,.()\-\?]*$/i
  RETURN result
```

### 3.2 Pseudo-code: String Decoding

To restore a BCS string to its raw format:

```text
FUNCTION decodeString(input):
  SET result = input
  result = REPLACE_ALL(result, "_",  " ")  // Underscores back to spaces
  result = REPLACE_ALL(result, "*n", "\n") // *n back to newlines
  result = REPLACE_ALL(result, "*u", "_")  // *u back to underscores
  RETURN result
```

### 3.3 Pseudo-code: Array Handling

Arrays are serialized into a single string using a specific multi-character
delimiter (`*c`).

```text
FUNCTION encodeArray(items):
  SET encodedItems = []
  FOR EACH item IN items:
    encodedItems.PUSH(encodeString(item))
  RETURN JOIN(encodedItems, "*c")

FUNCTION decodeArray(serialized):
  IF serialized EQUALS "":
    RETURN []

  SET parts = SPLIT(serialized, "*c")
  SET decodedItems = []
  FOR EACH part IN parts:
    decodedItems.PUSH(decodeString(part))
  RETURN decodedItems
```

## 4. Serialization Format

A Hat object is serialized as a single string composed of exactly 10 fields
separated by semicolons (`;`).

### 4.1 Structure

The fields MUST appear in this precise order:

1. market_hash_name (BCS Encoded)
1. flags (Character Sequence)
1. qualities (BCS Array)
1. unusualEffects (BCS Array)
1. killstreakers (BCS Array)
1. sheens (BCS Array)
1. warPaints (BCS Array)
1. paints (BCS Array)
1. spells (BCS Array)
1. killstreakParts (BCS Array)

### 4.2 State Flags String

The second field represents the four boolean states (`tradable`, `marketable`,
`craftable`, `festivized`) encoded as a single sequence of uppercase characters.

The characters are present in the string if and only if their corresponding
boolean state is `true`. When multiple states are `true`, they MUST appear in
the following sequence:

- `T` (Tradable)
- `M` (Marketable)
- `C` (Craftable)
- `F` (Festivized)

_(For example, an item that is Tradable and Craftable, but not Marketable or
Festivized, results in the exact flags string `TC`.)_
